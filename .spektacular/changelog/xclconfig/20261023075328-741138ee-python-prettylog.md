# Pretty logging with `xcl.prettylog`, and in-order asyncio events

Python programs can now turn on a readable, coloured log of everything xcl does with one line: `on_event=xcl.prettylog.handler(sys.stderr, xcl.prettylog.level_from_env())`, on `xcl.Config` or `xcl.aio.Config`. Each event is a line in the same layout Go's examples show; each created resource's configuration, including values the provider filled in, appears beneath its creation line as it happens; and a configuration mistake shows its report with the faulty source lines. The asyncio client now delivers events to `on_event` one at a time and in order, as the synchronous client and Go do.

> Derived from project xcl (spektacular), spec/plan 20261023075328-741138ee-python-prettylog. See the project-level record for the full feature.

## What changed in this repo

- New public module `xcl.prettylog`: `handler(file=None, level=logging.INFO, *, logger=None, formatter=None)`, `level_from_env()` and `LEVEL_ENV` (`"XCL_LOG_LEVEL"`). Standard library only; colours, formats and reports come from `xcl.highlight` and `xcl.format_error`. Created resources are shown at info and below (needs `event_data=xcl.EventDataLevel.PROCESSED`; a once-only line says so otherwise), reports beneath configuration mistakes at every level, one warning per resource that cannot be shown, nothing for variables, outputs and modules. `logger=` routes the same text through standard logging as one record per event.
- New private line layout `xcl/_prettyline.py`, a port of charmbracelet/log's text format and Go's value formatting.
- `xcl.aio.Config` delivers events through one consumer per operation: in order, one call at a time; state-store and function tasks stay concurrent; a handler's exception is still dropped. A handler that relied on overlapping calls is now serialised.
- Events remember the configuration that delivered them (privately, outside fields, equality and repr); both configuration flavours remember their event data level and have a private blocking saved-record render; the logging bridge's rules are shared helpers (its behaviour is unchanged).
- Tests: unit tests for the layout (against lines produced by Go), the handler, asyncio ordering and the plumbing; engine-backed tests for every acceptance criterion on both clients, including a pseudo-terminal; the parity program records `pretty_log` and the suite compares it with Go's on every fixture.
- README "Pretty logging" section and asyncio wording; PARITY.md pairs Go's `example/prettylog` with `xcl.prettylog`.

## Why

Python users had to write their own event handling and still could not see what each resource became. The pretty logger gives them the same log Go users get, held to Go's real output by the parity suite. Ordered asyncio delivery is what lets the asynchronous client produce the same lines.

## Release note

Add to the GitHub release notes: the asyncio client now delivers events to `on_event` one at a time and in order, so a handler that relied on running concurrently may slow an operation. The release must pin an xcl release carrying the parity program's `pretty_log` stage.
