# xcl-lang encodes the entities a program holds as configuration text

`cfg.encode_entity(entity)` turns any entity your program holds into xcl configuration text: one a lookup or an event returned, an instance of a registered class you built yourself, or a plugin's `xcl.Entity`. It takes `include_computed`, `include_empty`, `reveal_sensitive`, `show_references` and `highlight`, all off by default, and `cfg.encode_saved_entity` takes the same keywords. The text is identical to what a Go program writes for the same entity. Changes you make to a looked-up entity show in the text, and with `reveal_sensitive=True` a looked-up entity shows its configured secrets.

## What changed in this repo

- **API.** `xcl/config.py` adds `Config.encode_entity` and the four keywords on `encode_saved_entity`, through a shared `_encode_options`. `xcl/aio.py` adds the awaitable twins. The record is built before any engine call, so bad input fails without one.
- **Record builder.** `xcl/_schema.py` adds `record_of` and `record_bytes`, the mirror of hydration. Type and subtype come from the configuration's registration, the name from the label field or `meta.name`, fields go under their schema names, and a `Sensitive` is written as its value or the marker. `hydrate` remembers the JSON each instance came from, so untouched fields are written exactly as the engine gave them. `xcl/_entity.py` adds `Meta.to_record`.
- **Errors.** A value that is not an entity, an unnamed entity or a value JSON cannot write raises `NotEncodableError`. An unregistered class raises `NotRegisteredError`. Variables, outputs and modules are refused by the engine with `NotEncodableError`, and encoding during an operation raises `OperationInProgressError`.
- **Engine.** `xcl/_core/core_pb2.py` and `.pyi` are regenerated, and `xcl-ref.txt` pins `v0.11.0`.
- **Parity.** `tests/parity/run_python.py` writes the same `encode` section as Go. `tests/parity/types.py` adds the `encode` fixture's classes and hand-built instances, and the suite passes for every fixture.
- **Tests and docs.** Unit tests cover `record_of` and the options. Real-engine sync and asyncio tests cover every lookup kind, choices, edits, highlight, errors and refusal. README gains "Encoding entities as configuration", and PARITY.md lists `EncodeEntity` as supported.

## Why

Go programs could already write an entity as configuration text; Python could only render a saved record, without Go's choices. The engine does the rendering, and Python only builds the record, so the two languages cannot drift.
